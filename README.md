# Weather Analytics & Stormy

**Сервис сбора, хранения и анализа метеорологических данных на Python с интерактивным дашбордом и Telegram-ботом.**

Weather Analytics & Stormy — учебный проект по инженерии данных и аналитике, разработанный в рамках магистерской программы «Анализ и инженерия данных».

Сервис получает исторические погодные данные и прогнозы через Open-Meteo API, обрабатывает их с помощью ETL-процесса, сохраняет в PostgreSQL и предоставляет пользователям два интерфейса: аналитический дашборд Streamlit и Telegram-бот Stormy.

Проект охватывает полный цикл работы с данными — от API и проектирования базы данных до визуализации, автоматизированного тестирования и развёртывания на VPS.

## Возможности

### ETL и хранение данных

- Загрузка исторических и прогнозных метеорологических данных из Open-Meteo.
- Работа со справочником городов, координатами и часовыми поясами.
- Обработка суточных и почасовых погодных показателей.
- Получение дополнительных прогнозных показателей ECMWF.
- Проверка и преобразование данных перед сохранением.
- Загрузка в PostgreSQL с защитой от дублирования записей.
- Продолжение исторической загрузки с учётом уже сохранённых данных.
- Обработка ошибок API, логирование и контроль выполнения ETL.
- Поддержка локальных, первоначальных, регулярных и пакетных загрузок.

### Аналитический дашборд

**[Открыть Weather Analytics Dashboard](https://stormy-analytics.ddns.net/)**

Веб-приложение на Streamlit с интерфейсом на русском и английском языках. Позволяет исследовать исторические погодные данные, получать семидневные прогнозы и сравнивать климатические показатели городов.

**История (History)**

Исследование исторических погодных данных: температура, осадки, ветер, влажность, атмосферное давление и дополнительные метеорологические показатели. Доступны графики и просмотр исходных данных.

**Прогноз (Forecast)**

Семидневный прогноз с дневной и почасовой детализацией: температура и ощущаемая температура, осадки и их вероятность, ветер и порывы, влажность, точка росы, УФ-индекс, облачность, давление и видимость. Предусмотрены визуализация направления ветра и информация о Солнце и Луне.

**Сравнение (Comparison)**

Сопоставление двух городов по выбранным метеорологическим показателям. Доступны различные временные интервалы, сводные показатели и графики с автоматическим изменением детализации по дням, неделям, месяцам и годам.

### Telegram-бот Stormy

**[@StormyForecastBot](https://t.me/StormyForecastBot)** — диалоговый интерфейс для получения погодной информации.

Бот поддерживает:

- поиск и выбор городов;
- обработку текстовых погодных запросов;
- работу с датами и временными периодами;
- русский и английский языки;
- интерактивные кнопки;
- сохранение пользовательского состояния между перезапусками.

Для получения сообщений используется Telegram long polling.

## Архитектура

```text
                      Open-Meteo API
                            |
                     HTTPX API Client
                            |
                       Extractor
                            |
                       Transformer
                            |
                        Validator
                            |
                         Loader
                            |
                       PostgreSQL
                            |
               +------------+------------+
               |                         |
         Streamlit Dashboard       Telegram Stormy
         History / Forecast        Weather requests
         Comparison               City search
```

ETL реализован как отдельный процесс. Его оркестрация находится в `etl/pipeline.py`.

Основные этапы:

1. Инициализация PostgreSQL и проверка схемы.
2. Загрузка и проверка справочника городов.
3. Получение данных из Open-Meteo API.
4. Преобразование ответов API во внутреннюю структуру.
5. Проверка данных и подготовка записей.
6. Сохранение в PostgreSQL.
7. Регистрация результатов выполнения и логирование.

Исторические данные и прогнозные снимки хранятся отдельно. Это позволяет анализировать погодную историю и получать актуальные прогнозы без смешивания разных типов данных.

Подробное описание архитектуры, ETL-алгоритмов и обработки ошибок приведено в [технической спецификации](docs/technical_spec.md).

## Установка и локальный запуск

### Требования

- Python 3.12
- PostgreSQL
- Доступ к Open-Meteo API
- Telegram Bot Token для работы бота

### Установка

```bash
git clone https://github.com/marinaorlenko/weather-analytics.git
cd weather-analytics

python3.12 -m venv venv
source venv/bin/activate

python -m pip install -e '.[dev]'
```

Создайте `.env` на основе `.env.example` и укажите параметры PostgreSQL, Open-Meteo и Telegram.

### Основные переменные конфигурации

| Переменная | Назначение |
|---|---|
| `FORECAST_URL` | Open-Meteo API для получения прогноза погоды |
| `GEOCODING_URL` | Open-Meteo API для поиска городов и координат |
| `ARCHIVE_URL` | Open-Meteo API для загрузки исторических данных |
| `ECMWF_URL` | Open-Meteo ECMWF API для дополнительных прогнозных показателей |
| `HTTP_TIMEOUT` | Тайм-аут HTTP-запросов в секундах |
| `DB_HOST` | Адрес сервера PostgreSQL |
| `DB_PORT` | Порт PostgreSQL |
| `DB_USER` | Пользователь PostgreSQL |
| `DB_PASSWORD` | Пароль PostgreSQL |
| `DB_NAME` | Имя базы данных |
| `TELEGRAM_BOT_TOKEN` | Токен Telegram-бота |

Пример `.env` для локальной разработки:

```dotenv
# Open-Meteo public API endpoints
FORECAST_URL=https://api.open-meteo.com/v1/forecast
GEOCODING_URL=https://geocoding-api.open-meteo.com/v1/search
ARCHIVE_URL=https://archive-api.open-meteo.com/v1/archive
ECMWF_URL=https://api.open-meteo.com/v1/ecmwf

# HTTP configuration
HTTP_TIMEOUT=15

# Database
DB_HOST=localhost
DB_PORT=5432
DB_USER=your_username
DB_PASSWORD=your_password
DB_NAME=weather_analytics

# Telegram Bot
TELEGRAM_BOT_TOKEN=your_token
```

Режим выполнения определяется параметром `APP_ENV`. По умолчанию используется `local`. При запуске через Docker Compose на сервере автоматически устанавливается `APP_ENV=server`, поэтому добавлять эту переменную в локальный `.env` необязательно.

Секреты и пароли хранятся в `.env`, который не должен попадать в репозиторий.

### Локальный ETL

Для локальной разработки используется режим `local`:

```bash
python main.py --mode local
```

Он обрабатывает ограниченную выборку городов и короткий исторический период, заданные в конфигурации. Режим предназначен для проверки логики без массовой загрузки истории на локальный компьютер.

### Запуск дашборда

```bash
python -m streamlit run dashboard.py
```

### Запуск Telegram-бота

```bash
python -m weather_analytics.bot.telegram_bot
```

Для работы интерфейсов необходима доступная база PostgreSQL с загруженными данными.

## Режимы ETL

Приложение поддерживает пять режимов:

| Режим | Назначение |
|---|---|
| `local` | Ограниченная локальная загрузка истории и прогноза |
| `initial` | Первоначальная загрузка исторических данных на сервере |
| `daily` | Регулярное пополнение исторических данных |
| `forecast` | Обновление прогнозных данных |
| `batch` | Пакетная историческая загрузка с заданными параметрами |

Примеры запуска:

```bash
python main.py --mode local
```

```bash
python main.py --mode initial
```

```bash
python main.py --mode daily
```

```bash
python main.py --mode forecast
```

Для пакетной загрузки:

```bash
python main.py --mode batch \
  --start-date 2025-01-01 \
  --end-date 2025-01-31 \
  --cities Dubai Moscow \
  --max-periods 10
```

Серверные режимы требуют `APP_ENV=server`. Параметры `--start-date`, `--end-date`, `--cities` и `--max-periods` доступны через CLI только для `batch`.

Историческая загрузка разбивается на периоды. Уже сохранённые данные учитываются при продолжении обработки, а ограничения PostgreSQL предотвращают появление конфликтующих записей.

Для защиты от чрезмерного количества запросов используется ограничение частоты обращений к API.

## Логирование и мониторинг ETL

В проекте реализовано централизованное логирование ETL-процессов
на основе стандартного модуля Python `logging`.

Настройка выполняется классом `StormyLogger` в модуле
`src/weather_analytics/logging_config.py`.

Журналы записываются одновременно в консоль и в каталог `logs/`.

### Параметры логирования

| Параметр | Значение |
|---|---|
| Уровень | `INFO` и выше |
| Формат файла | `etl_YYYY-MM-DD.log` |
| Каталог | `logs/` |
| Срок хранения | 14 дней |
| Очистка | При запуске ETL |
| Формат записи | Время, уровень, модуль, сообщение |

Логируются основные этапы загрузки, количество обработанных данных,
ошибки API, преобразования и сохранения данных.

Для ошибок используются сообщения уровня `ERROR` и `exception`
с информацией о возникшем исключении.

Дополнительно результаты запусков ETL сохраняются в таблице
PostgreSQL `etl_runs`, а состояние исторической загрузки — в `etl_state`.

### Просмотр журналов

Локально:

```bash
tail -f logs/etl_$(date +%Y-%m-%d).log
```

На VPS:

```bash
docker compose --env-file .env \
  -f deploy/compose.yaml logs -f etl
```

Файлы журналов ETL сохраняются на сервере через Docker volume
mapping `../logs:/app/logs`.

Каталог `logs/` исключён из Git и не включается в репозиторий.

## Работа на VPS

Серверное развёртывание организовано с помощью Docker Compose.

В `deploy/compose.yaml` определены следующие сервисы:

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 16 с постоянным Docker volume |
| `db-init` | Инициализация базы и схемы |
| `dashboard` | Streamlit-приложение |
| `bot` | Telegram-бот Stormy |
| `etl` | Отдельный контейнер для загрузки данных |

PostgreSQL и Streamlit внутри Docker привязаны к `127.0.0.1` сервера. Внешняя публикация дашборда требует отдельной настройки сетевого доступа или reverse proxy.

### Запуск серверных сервисов

Из корня проекта:

```bash
docker compose --env-file .env \
  -f deploy/compose.yaml \
  up -d --build db dashboard bot
```

Сервис `db-init` выполняется как зависимость после проверки готовности PostgreSQL.

### Запуск ETL на сервере

ETL работает как отдельное задание и не запускается автоматически при каждом обновлении приложения.

Пример регулярной исторической загрузки:

```bash
docker compose --env-file .env \
  -f deploy/compose.yaml \
  run --rm etl python main.py --mode daily
```

Обновление прогноза:

```bash
docker compose --env-file .env \
  -f deploy/compose.yaml \
  run --rm etl python main.py --mode forecast
```

Для автоматического выполнения ETL требуется настроенное расписание на сервере.

Постоянное хранение PostgreSQL организовано через Docker volume `postgres_data`. Данные пользовательского состояния Telegram-бота и рабочие файлы ETL размещаются в соответствующих каталогах проекта.

## CI/CD

Автоматизация реализована через GitHub Actions:

```text
.github/workflows/deploy.yml
```

Workflow запускается при отправке изменений в ветку `main` или вручную.

**CI**

1. Подготовка Ubuntu 24.04 и Python 3.12.
2. Запуск тестового PostgreSQL 16.
3. Установка зависимостей.
4. Проверка Ruff.
5. Проверка форматирования.
6. Запуск pytest.

**CD**

После успешного прохождения CI выполняется подключение к VPS по SSH, получение актуальной версии проекта и обновление Docker-сервисов.

В процессе деплоя обновляются PostgreSQL, Streamlit и Telegram-бот. Массовая историческая загрузка не запускается автоматически.

Доступ к VPS настраивается через GitHub Actions Secrets.

### Интеграционное тестирование PostgreSQL

Интеграционные тесты используют отдельную временную базу данных
`weather_analytics_test`, которая автоматически создаётся перед
тестированием и удаляется после завершения тестовой сессии.

Структура таблиц создаётся на основе SQLAlchemy-моделей. Перед каждым
интеграционным тестом таблицы очищаются, что обеспечивает изоляцию тестов.

Рабочая база данных не изменяется. Если тестовая база уже существует,
тестирование прерывается во избежание случайного удаления данных.

Для запуска необходим работающий PostgreSQL и пользователь с правами
на создание и удаление баз данных.

```bash
python -m pytest -q
```

## Источники данных и ограничения

Основной источник данных — [Open-Meteo](https://open-meteo.com/).

Проект использует исторические, прогнозные и географические данные, предоставляемые Open-Meteo. Доступность отдельных показателей зависит от API, погодной модели, города и временного периода.

При использовании данных необходимо соблюдать актуальные условия Open-Meteo, включая требования к атрибуции и применимые ограничения использования.

### Ограничения бесплатного API

| Период | Максимальное количество API-вызовов |
|---|---:|
| Минута | 600 |
| Час | 5 000 |
| День | 10 000 |
| Месяц | 300 000 |

Лимиты применяются по IP-адресам и приложениям. При превышении допустимой нагрузки доступ к API может быть ограничен.

Количество учитываемых API-вызовов не всегда совпадает с количеством HTTP-запросов. Запросы с большим числом метеорологических переменных или продолжительными временными интервалами могут учитываться как несколько вызовов.

При проектировании ETL учитываются ограничения API: загрузка исторических данных выполняется по периодам, а обращения к API регулируются настройками HTTP-клиента и ETL.
